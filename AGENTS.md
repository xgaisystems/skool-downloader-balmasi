# Skool Downloader - Developer Onboarding

## Project Goal & Context
The goal of this project is to provide a robust, platform-independent tool for creating local, offline backups of Skool.com courses. This includes downloading video content, localizing images, and generating a navigable HTML structure that mirrors the online classroom.

## Technical Architecture

### Core Tech Stack
- **TypeScript / Node.js**: Modern ESM environment.
- **Playwright**: Used for scraping and the initial manual authentication flow.
- **yt-dlp**: Handled via `yt-dlp-wrap`. It's downloaded on first run into a per-user cache folder (`resolveCacheDir()` in `src/downloader.ts`, override with `SKOOL_DOWNLOADER_CACHE_DIR`) to avoid system-wide installations. It is deliberately not stored under the current directory or the package root. The binary is kept current automatically; see **Keeping yt-dlp current** below.
- **Axios**: For direct asset (image) downloads.

### Key Technical Strategies
1. **Source of Truth (`__NEXT_DATA__`)**:
   Instead of fragile DOM scraping, the tool extracts the `__NEXT_DATA__` JSON block from Skool's page source. This contains the structured course hierarchy, lesson metadata, and direct video links.
2. **Manual Authentication**:
   A script (`npm run login`) opens a browser for manual login, then captures the `storage_state.json`. 
3. **Cookie Conversion**:
   The tool automatically converts Playwright's JSON cookies into the **Netscape format** (`cookies.txt`) required by `yt-dlp` to access private course videos.
4. **Rich Text Parsing**:
   Skool uses TipTap/ProseMirror for lesson content. The scraper includes a parser (`parseTipTap`) to convert the stringified JSON content back into clean, localizable HTML. Skool renames some nodes: the bullet list is `unorderedList` (not `bulletList`), and mentions are inline `user-mention` (`@label`) and `course-reference` (`#label`) nodes whose text is only in `attrs.label`. An unknown block type falls back to a `<div>`, which for a list leaves bare `<li>`s that break the surrounding list; an unknown inline node is dropped with its text.
5. **Asset Localization**:
   The `Downloader` class identifies `<img>` tags, downloads the images into a local `assets/` folder, and rewrites the HTML sources before saving.
6. **Native Video Extraction**:
   Skool's native Mux player requires a "play" click to generate authenticated HLS manifest URLs. The scraper simulates this interaction and monitors performance entries to extract the signed `.m3u8` link.
7. **Resource/Attachment Downloads**:
   Course attachments (PDFs, DOCX, etc.) are downloaded using direct API calls to `https://api2.skool.com/files/{file_id}/download-url?expire=28800`. This is more reliable than DOM interaction and returns signed CloudFront URLs for downloading.
8. **Community Posts Linked to a Lesson**:
   Cards under a lesson body are posts pinned to it. They are listed in the lesson's `pageProps.pinnedPosts`, which truncates the text at `metadata.contentLimit` and omits `attachmentsData`, so `extractLinkedPosts()` opens each post page (`postTree.post`) and only falls back to the partial copy, flagged as incomplete, if that fails. Everything else comes from the API, called from that page with `fetch` so it carries the session (`skoolApi()`):
   - **Videos** uploaded to Skool are ids in `metadata.videoIds` (`video_ids` in comments). The post page signs its own in `postTree.videos` (`playbackId` + `playbackToken`, valid about a day); any other id is signed with `POST /videos/{id}/request-data`, as Skool's player does. Both become `stream.video.skool.com/<playbackId>.m3u8?token=…` for yt-dlp. Not signed when videos are skipped.
   - **Comments** are not in the page: `GET /posts/{id}/comments?group-id=…&limit=25`, replies nested as `children`. The next page is `created-gt=<last>` until `last` is 0. `last` is a nanosecond timestamp beyond a JS number's precision, so it is read from the raw text. The response includes each member's email, which must never be stored.
   - **Comment files** are ids in `metadata.attachments`: `GET /files?ids=a|b` for names, and `POST /files/{id}/download-url` when there is no `read_url`.

   `saveLinkedPost()` (`src/linked-post-archive.ts`) stores everything in `posts/<post-slug>/` inside the lesson: the files of the post and of its comments in one folder, `video-NN.mp4` and `comentario-NN-video-NN.mp4`, and `post.html`, one self-contained page (images as `data:` URIs, no script) with the post and every comment. The lesson card links to it, the lesson's resources list it as "Fuente", and `lesson.json` gets a `linkedPosts` summary. A failed post video is a `video` failure of the lesson. Content is Markdown written by any member: `src/linked-posts.ts` escapes raw HTML, drops non-web URLs, expands Skool's `[ul][li]` lists and turns `obj://course/<id>` links into the local lesson (or Skool when it is not part of the download). It must keep escaping because the pages share an origin with the local progress API. External video links (YouTube, Loom) are kept as links. Visits and API calls are spaced (`POST_NAVIGATION_DELAY_MS`, `API_REQUEST_DELAY_MS`) because bursts get a CloudFront 403 for the whole site.
9. **Keeping yt-dlp current**:
   A pinned yt-dlp rots, because its value is almost entirely in extractors that break when a video host changes (issue #14). `Downloader.init()` reads the installed version, which is a release date, and if it is older than `STALE_AFTER_DAYS` it compares against the newest GitHub release and installs it. A stamp file (`.yt-dlp-check.json`) limits this to one check per day; `init()` is memoised, so it is also at most once per run. Three rules matter when changing this code:
   - The update **blocks** the run instead of happening in the background. A background refresh would leave the current run on the binary that is already broken, which is the failure being fixed.
   - A download is written to a `.tmp` path and executed there before it is renamed into place. `YTDlpWrap.downloadFromGithub` is not used: it writes the response body before checking the status code, and attaches no error handler to the write stream, so a 404 or a read-only folder yields a corrupt binary or an uncaught exception. `downloadFile()` in `src/downloader.ts` replaces it.
   - A failed update must never fail a download. Everything except an unusable binary is caught, logged and continued past.

   The copy being replaced is kept as `yt-dlp.prev` for `skool update --rollback`. `SKOOL_NO_YTDLP_UPDATE=1` switches the automatic check off.
10. **High-Performance Downloads**:
   The downloader is optimized with `-N 16` for parallel fragment fetching and `ffmpeg` post-processing (`+faststart`) for instant in-browser playback.
11. **ffmpeg Fallbacks**:
   `findFfmpegCandidates()` collects `SKOOL_FFMPEG_PATH`, the bundled `ffmpeg-static` and the one on `PATH`, runs `-version` on each (dropping any that does not run, and duplicates by real path), and orders them newest version first, with `SKOOL_FFMPEG_PATH` always leading; nightly builds without a release number go after numbered ones. With none usable, the CLI (`ensureFfmpeg()`, before any download) warns and, in a TTY, offers `installBundledFfmpeg()`, which runs ffmpeg-static's own `install.js` to fetch the build for the OS/arch; without a TTY it prints the install hints and exits 1. The bundled build (ffmpeg-static 5.3.0, ffmpeg 7.0.2) segfaults in its MPEG-TS demuxer on some Loom HLS streams, even when only reading them; yt-dlp then reports `ERROR: Postprocessing:` followed by an ffmpeg progress line, not the crash. `downloadVideo()` retries a postprocessing failure with each other ffmpeg and finally with `-f b`, the best format that already holds video and audio (Loom's `http-transcoded` mp4 at full resolution), which needs no merge. Leftovers of a failed attempt (`.fhls-raw-*`, `.temp.mp4`, `.part`) are deleted before each retry and after giving up. Other failures are not retried. npm 12+ skips install scripts unless they are listed in `allowScripts` in `package.json`; `ffmpeg-static` must stay listed there (its version is part of the key) or a fresh install has no bundled binary.
12. **Failures Are Reported, Not Swallowed**:
   A video that fails used to be a warning and the lesson was counted as completed. Now each lesson task records failures (`LessonFailure`, kind `video` or `lesson`) and throws after saving whatever it could, so both task renderers show it as failed. `runConcurrent()` catches per task so one failure never stops the rest. `DownloadSummary` carries `failedVideos` and the `failures` list, `lesson.json` stores `videoError`, and `.download-failures.json` is written next to the course (removed after a full clean run). In interactive mode the logger queues warnings while a task renderer owns the terminal (`deferredLogs` in `src/cli.ts`), because both renderers redraw over anything printed meanwhile; the queue is printed when the run ends.
13. **Which Courses Are Locked**:
   `filterAccessibleCourses()` trusts `metadata.hasAccess` and only falls back to `privacy > 0` when Skool leaves `hasAccess` out. Gated courses keep `privacy: 1` for members who unlocked them, so treating `privacy` as "locked" skipped every course of such communities and multi-course downloads saved nothing.
14. **Interrupting a Download**:
   `registerShutdownHandlers()` in `src/index.ts` regenerates the course and group index on SIGINT/SIGTERM and exits with 130/143. It goes through `indexLimit`/`groupIndexLimit` (after clearing their queues) so it never writes `index.html.tmp` at the same time as a regular regeneration. Nothing else may call `process.exit` on SIGINT during a download: Listr runs with `registerSignalListeners: false` and the multi-column renderer only stops drawing.
15. **Asset Downloads**:
   `downloadAsset()` streams into `<file>.part` with `pipeline()` and renames at the end. `pipe()` does not forward a response error to the file, so a dropped connection used to leave the promise pending forever and hang the lesson and every course queued after it; and a partial file at the final path has a non-zero size, so later runs skipped it as complete. axios' `timeout` is an idle timeout on the socket in Node, so it also aborts a body that stops arriving.
16. **Progress Tracking and the Local Server**:
   Lesson, course and community pages carry a "done" tick. The browser code is generated in one place, `src/progress-sync.ts`: a shared runtime (localStorage, a `window.name` mirror for `file://` navigation, BroadcastChannel, and the `/api/progress` + `/api/events` SSE endpoints of `skool serve`) plus a small page-specific `render(data)`. A lesson's id is `<course folder>/<relative path of its index.html>`. `regenerateIndex()` swaps the script of saved lesson pages for the current one, located by its `STORAGE_KEY` line (the match must stay inside one `<script>` element: a lazy match from the first `<script>` deleted the video player's script), but only when `patchLessons` is on: the regeneration that runs after every downloaded lesson passes `false`, otherwise each lesson finished rewrote every lesson page of the course. `src/server.ts` serves `downloads/` on `127.0.0.1:${PROGRESS_SERVER_PORT}` (3100) by default and answers CORS only for `Origin: null`, i.e. `file://` pages; a busy port is an error rather than a silent move, because `file://` pages only know `PROGRESS_SERVER_PORT`. Anything rendered from Skool data into these pages must be escaped: they share an origin with the progress API.
17. **Being Gentle with Skool**:
   Skool detects automated traffic and can cut an account's access. Keep lesson concurrency modest, keep the delays between navigations (`POST_NAVIGATION_DELAY_MS`, the waits in `extractLessonData()`), and never test against skool.com in loops: stub `Scraper`/`Downloader` methods for orchestration tests and use a local HTTP server for download tests.

18. **Vimeo Videos**:
   Skool lessons embed Vimeo videos that are restricted to certain domains. `vimeo.com/<id>` answers "The web client only works when logged-in" even with cookies, because only the embed player honours the Referer. `downloadVideo()` therefore rewrites Vimeo URLs with `vimeoPlayerUrl()` (`https://player.vimeo.com/video/<id>?h=<hash>`) and sends `Referer:https://www.skool.com` **without the trailing slash**: with the slash Vimeo answers 401 (checked with yt-dlp 2026.10.21). Other hosts keep the slash.
   **Cloudflare also blocks yt-dlp's TLS fingerprint**: after a burst of requests Vimeo answers 401 / "blocked due to its TLS fingerprint" to every video, including ones that worked minutes earlier (a real browser passes the Turnstile challenge). The Python `yt-dlp` zipapp cannot impersonate a browser; the standalone builds bundle `curl_cffi`, and yt-dlp uses it on its own. `ytDlpAssetName()` therefore installs `yt-dlp_linux` / `yt-dlp_linux_aarch64` / `yt-dlp_macos` / `yt-dlp.exe`, falling back to the zipapp only on other platforms. The asset is recorded in `.yt-dlp-check.json`; a copy installed with a different asset (anything installed before this) is replaced on the next run, ahead of the age and once-a-day checks, and a failed switch only warns. Same file name `yt-dlp` in the cache folder.

19. **YouTube Audio Tracks and Subtitles**:
   For a YouTube URL (`isYouTubeUrl()`, `src/youtube.ts`) `downloadVideo()` first runs `yt-dlp -J` and `planYouTubeDownload()` decides what to add for the languages of `SKOOL_YOUTUBE_LANGS` (default `es,en`, in track order). With two or more of them as audio tracks (original + dubs), it uses `--audio-multistreams -f bv*+ba[language^=es]+ba[language^=en]/bv*+ba/b`. YouTube tags every audio stream with the original's language and yt-dlp's merger sets none, so `--postprocessor-args Merger:-metadata:s:a:N language=…` names them (a `Merger:` value is added to the `ffmpeg:` ones, not a replacement). Subtitles: uploaded ones first, YouTube's automatic ones only for a language without them, by exact key (a pattern like `en.*` fetches every machine translation); they are embedded (`mov_text`) and kept as `video.<lang>.vtt` for the lesson page's player (**Video Player** below). A subtitle error (YouTube answers 429 to bursts of caption requests) fails yt-dlp's whole run, so it is retried with the audio tracks but no subtitles, and the subtitles are then fetched alone, one language at a time, waiting 5/30/90 s on each 429 (`fetchSubtitlesLater()`; those are only `.vtt` files, not embedded). Any other failure of the multi-language attempt, or a failed probe, retries as a plain download, still followed by the subtitles. YouTube calls also pass `--js-runtimes node:<process.execPath>`, since yt-dlp only looks for deno and without a JS runtime gets fewer formats. 
20. **Video Player**:
   Chrome and Firefox play only the first audio track of an mp4 and cannot switch, and Chrome refuses `<track>` files on `file://` pages, so `renderVideoPlayer()` (`src/video-player.ts`) gives the lesson page its own controls when the video has more than one audio track or any subtitle (otherwise it is the plain `<video controls>`, which is also what shows without JavaScript). `Downloader.prepareTracks()` copies every audio track but the first (`-c copy -f mp4`: the m4a muxer refuses Opus) to `video.<lang>.m4a` and writes `video.tracks.json` (**Track Origins** below); it also runs when the video already exists. Choosing another language mutes the video and plays that file in an `<audio>` kept in step: a gap over 1 s is a seek, a smaller one is closed by playing the audio up to 8 % faster or slower, because a seek always leaves it ~0.3 s behind. Checked from `requestAnimationFrame` and `timeupdate` (rAF stops in background tabs). Subtitles are parsed from the `.vtt` files at page generation (`parseVtt()`). YouTube's automatic captions (and their machine translations) come as ~1 s cues of a few words, each repeated as the first line of the next, with a `<00:00:01.230>` tag per word; shown as they are they flash past. When those tags are present, `regroupWordTimedCaptions()` rebuilds the word sequence from each cue's new line and regroups it as YouTube's player does: up to 84 characters in two balanced lines, cut at a sentence end or a pause over 2 s, each kept until the next starts (at most 2.5 s after its last word). Other subtitles keep their timing, minus tags, 10 ms filler cues and repeats. The cues are embedded as JSON with `<` escaped, then drawn with `textContent`, so they work on `file://` and in fullscreen. Playback controls sit over the picture; the languages are a panel of buttons under it (🔊 Audio / 💬 Subtítulos, after the hand-made lesson pages this replaced), which stays visible in fullscreen because the whole player, not the `<video>`, goes fullscreen. Audio, subtitle, speed and volume choices are remembered in `localStorage` (`skool-player-prefs`). Under 640 px the controls go below the picture.

21. **Track Origins**:
   Automatic subtitles are poor, and a later step will re-translate and re-subtitle lessons, so it has to tell them from ones a person wrote. `video.tracks.json` (`src/media-tracks.ts`) records, per audio track, `kind` (`original`/`dubbed`), `generated: "auto"` when YouTube calls the dub automatic (`dubbed-auto` in the format note; a dub without it is not claimed as automatic), and YouTube's `note`; per subtitle, `origin`: `manual`, `auto-asr` (speech recognition of what is said), `auto-translated` (+ `translatedFrom`), `auto` (automatic, kind unknown) or `unknown`, plus `generator`. The facts come from the `yt-dlp -J` probe (`planYouTubeDownload()`: `info.language` or the `-orig` caption key is the original language; an automatic caption in another language is a translation). A YouTube video already saved without `source` in its manifest is probed once (no download) by `factsForSavedVideo()`; without a probe, a `.vtt` with YouTube's per-word tags is `auto`. Each classified `.vtt` also gets `NOTE skool-downloader: origin=… translatedFrom=… generator=…` after its header, and `lesson.json` a `media` summary. Without new facts, an earlier entry is kept, and entries/files another tool added (any other `origin`, e.g. `improved`) are never rewritten; when a language has several subtitles the player shows the non-automatic one. On the page: `· AUTO` on automatic subtitle buttons and `· doblaje` on dubbed audio, the detail in `title`, `data-origin`/`data-translated-from`/`data-kind`/`data-generated` on the buttons, and a notice under them while an automatic subtitle is on. Text subtitles inside the video file (`mov_text`, `subrip`, `webvtt`, `ass`...; Vimeo downloads carry them) are extracted by `prepareTracks()` to `video.<lang>.vtt` when that language has no file yet, as `origin: "unknown"`, `extractedFrom: "embedded"`: the file does not say who wrote them; picture subtitles (DVD/PGS) cannot become WebVTT. With videos skipped, `prepareTracks()` still runs on a `video.mp4` already in the lesson folder (it resolves ffmpeg itself, without `init()`), so a video added by hand gets them too. A lesson's video is `video.mp4`, or else the only `.mp4` in the lesson folder (`findLessonVideo()`): videos are often downloaded by hand and keep their own names (`February 19th.mp4`, `video1944708595.mp4`), which are not changed; their tracks take that name (`February 19th.en.vtt`, `February 19th.tracks.json`), `lesson.json` gets `videoFile`, and a download does not fetch the lesson's video again as `video.mp4`. Several `.mp4` and no `video.mp4` is not guessed at. `skool regenerate-index` (lesson pages patched) also runs `prepareTracks()` on every lesson with a video, rebuilds its player from the files on disk and sets `hasVideo`/`media` in `lesson.json`, all without visiting Skool: this is how improved subtitles added later reach the page. The player sits between `<!-- skool-video-player -->` markers for that (`replaceVideoPlayer()` also recognises any plain `<video>` element whose `src` is the lesson's video, as older pages and hand edits have; a page with neither gets the player after its `<h1>`). It replaced `video.audio.json`, which is deleted when found.

## Project Structure
- `src/auth.ts`: Handles the manual login flow and cookie conversion.
- `src/scraper.ts`: Navigates the course tree and parses lesson metadata from Next.js state.
- `src/downloader.ts`: Wrapper for `yt-dlp` and logic for image localization and resource downloads.
- `src/cli.ts`: Interactive CLI entry point (login, download course, download multiple courses, download single lesson, serve, regenerate index, update yt-dlp). Runs lesson downloads concurrently with per-lesson status: Listr2 when the lessons fit the terminal, a multi-column view (`runMultiColumnTasks`) when they do not. Prints the failure summary after each course.
- `src/index.ts`: Core download orchestrator. Handles course parsing, output path resolution, lesson processing, and manifest/index generation. Exposes callbacks + task runner hooks for the CLI.
- **Single Lesson Extraction**: The tool detects `?md=` or `?lesson=` in the input URL to download only a specific lesson instead of the entire course, and reports the exact destination path.
- **Native Video Handling**: Automates interaction with the Mux player to capture signed tokens.
- **Resource Downloads**: Uses direct API calls to fetch signed download URLs for attachments, stored in `resources/` folder within each lesson.
- `src/linked-posts.ts`: Sanitised Markdown rendering, the HTML of the community posts embedded in a lesson page, and the standalone `post.html` with comments.
- `src/linked-post-archive.ts`: Saves a linked post: its files, its videos, those of its comments, and `post.html`.
- `src/youtube.ts`: Audio-track and subtitle choice for YouTube videos.
- `src/video-player.ts`: The lesson page's video player (audio track and subtitle selection).
- `src/media-tracks.ts`: `video.tracks.json`, the origin of each audio track and subtitle (original/dubbed, manual/automatic).
- `src/progress-sync.ts`: Browser code for the "done" ticks shared by all generated pages, and `PROGRESS_SERVER_PORT`.
- `src/server.ts`: `skool serve`, the local static server for `downloads/` with the progress API and SSE.
- `bin/skool.js`: The published CLI shim. The `yt-dlp` binary lives in the per-user cache folder, not here.
- `src/utils.ts`: Shared utilities including European date and time formatting (`dd/mm/aaaa`) and `resolveDownloadsDir()`, the one place that decides the downloads folder (`SKOOL_DOWNLOADS_DIR`, else `downloads/` under the current directory). A configured folder that is missing, not a folder or not writable falls back to `downloads/` with a warning; only its last segment is created, because creating the parents would write under an unmounted mount point. The result is memoised per run.
- `src/env.ts`: Loads the gitignored `.env` next to `package.json`. `cli.ts` imports it first because some modules (e.g. `downloader.ts`) read their variables at load time.

### Date Formatting Standard (European Format: dd/mm/aaaa)
All user-facing dates across the codebase (HTML index/course templates, chips, course manifests display, CLI output, and log messages) MUST strictly follow the European format: `dd/mm/aaaa` (e.g., `01/10/2026`), or `dd/mm/aaaa HH:mm:ss` when including timestamps with time.
- Always use the helper functions in `src/utils.ts`: `formatDate()` and `formatDateTime()`.
- NEVER use raw, parameterless `new Date().toLocaleDateString()` or `new Date().toLocaleString()`, as Node.js and system locales frequently default to the US format (`m/d/yyyy`).

### Course Header & Cover Images Standard (Must fit completely: `contain`)
All course header photos and cover images across all generated HTML templates (course page hero banner `.hero-image img`, community page hero banner `.hero-image img`, and course card thumbnails `.course-image img`) MUST fit completely and intact in their designated space without being cropped, clipped, or distorted (`object-fit: contain`).
- Always use `object-fit: contain` with proper centering (`display: flex; align-items: center; justify-content: center;`) and a dark/neutral container background (`#020617` or `--panel-2`) so photos of any aspect ratio (e.g., Skool's ~1.94:1 covers or 16:9 portadas) are 100% visible inside their designated area without clipping logos, titles, or artwork boundaries.
- NEVER use `object-fit: cover` on course headers or card thumbnails, as it crops essential text, logos, or artwork edges.


- **ffmpeg Version**: The bundled `ffmpeg-static` is ffmpeg 7.0.2 and crashes on some Loom streams (see **ffmpeg Fallbacks**). A newer bundled build would remove the need for the fallbacks.
- **Rate Limiting & Detection**: Skool may implement rate limiting. The current implementation uses a fixed delay between navigations, but for very large courses, further randomization or human-like interaction patterns should be implemented in `scraper.ts`.
- **Local Chromium**: Playwright currently uses the system cache for browser binaries. For a 100% self-contained folder, configure `PLAYWRIGHT_BROWSERS_PATH=0` in `.env` to force local installation.
- **Internal Link Mapping**: Lesson content often contains links to other lessons or attachments. These are currently absolute URLs. A post-processing step could map these to the local file structure for a fully isolated backup.
